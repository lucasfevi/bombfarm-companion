# Localization (game terms + chrome)

**Status:** hard truth  
**Sources:** `english-game-terms`, `portuguese-ux-copy`

## Language policy

1. **UI chrome** is bilingual via `apps/web/src/shared/i18n` (`Lang = 'pt' | 'en'`). Default remains `pt` unless product changes it.
2. **Game terms follow `Lang`.** When `Lang === 'en'`, abilities, ability effect text, hero/item rarities, houses, slots, sheet/team-buff labels, props, equipment set names, and composed item display labels are English. When `Lang === 'pt'`, show Portuguese (official in-game names for abilities/houses where applicable; natural PT for set names).
3. **Internal IDs/keys stay PT-key stable** — do not rename storage/schema keys (`Comum`, `ponta_diamante`, slot `arma`, prop `minerio_mithril`, set slug `clay`, …). Localization is display-layer only.
4. **Display maps** live in `packages/domain/src/game-labels.ts` (helpers such as `abilityName`, `rarityLabel`, `slotLabel`, `propLabel`, `setName`, `formatItemDisplay`). UI must not render raw `AbilityDef.name` / catalog PT labels without going through helpers when `Lang` matters.
5. **User-entered hero names** are never auto-translated.

## Portuguese chrome quality

1. PT UI chrome (buttons, metrics, guides, tips, import dialog) should read as **natural PT-BR**, concept-level — not word-for-word EN calques.
2. **Do not rename official in-game ability or house names** in PT to invent marketing aliases.
3. Prefer a glossary of recurring terms (uptime → tempo ativo, etc.) and reuse it consistently. Bare EN leftovers in PT must be listed with rationale or rewritten.
4. Import dialog chrome has two steps: upload (`importDialogTitle` / `importDialogDesc`) and preview (`importPreviewTitle` / `importPreviewDesc`). Preview account totals reuse Account panel keys such as `treeTeamCoin` — do not bring back lecture copy (`importAccountLead` / `importAccountVerify`).

## EN copy quality

Prefer community-usable English for abilities/effects — not machine-literal calques. Keep effect numbers aligned with modeled `AbilityEffect` math.

## Player-facing plain language

UI chrome, tips, empty states, banners, and other **player-facing** i18n strings must read as product copy for players — not implementation notes for engineers.

1. **No formulas, pseudo-code, or API shapes** in chrome strings (`max(…)`, `effectiveUpgrade = …`, camelCase identifiers, field paths, JSON keys, type names).
2. **Say what the player should expect**, not how the code computes it. Prefer outcomes and actions over algorithms.
3. **Technical math belongs only** in dedicated explain surfaces that already use a separate `code` / formula channel (e.g. Explain Math). Even there, surrounding prose stays plain; put symbols in the code block, not inline in the paragraph.
4. **Internal docs, comments, ADRs, and domain types** may keep precise formulas — that is not a license to paste them into `apps/web/src/shared/i18n`.

```text
❌ Items below this level appear in the forge list; scoring uses max(item, floor).
✅ Items below this level show up in the forge list. The plan treats every item as at least this forge level.

❌ Scoring assumes … (effectiveUpgrade = max(item upgrade, floor)).
✅ The search treats every pool item as forged up to at least your minimum forge.
```
